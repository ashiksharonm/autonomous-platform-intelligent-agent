# Architecture

## What does the memory system store, and why is it structured this way?

Two SQLite tables, no vector store. `capabilities` holds one row per operation the agent can perform, built-in or synthesized, with `success_count`, `failure_count`, `total_api_calls`, `total_latency_ms`, and a `known_constraints` JSON list (things like "label must exist before use in create_issue"). `runs` and `steps` hold every instruction ever executed, tagged with a `task_type` (a stable snake_case label like `create_labeled_issue`), the exact step sequence used, and per-step outcomes.

I picked structured fields over embeddings on purpose. A vector store answers "what's semantically similar to this prompt," which is useful for retrieval and useless for deciding what to *do differently*. Repeat-detection here is exact `task_type` equality, not similarity search, because what needs to persist is the outcome of specific operations, not the prompt text. On a new instruction, `execution_memory.derive_guidance(task_type)` computes two concrete things from real history: `avoid_ops` (ops with a >50% failure rate for this task_type) and `preferred_decomposition` (the step sequence from the last fully successful run). Both feed the decomposition prompt. The part that actually matters is that `executor.apply_memory_guard()` also enforces memory in plain Python, independent of whatever the LLM decides. If a chosen step uses an op in `avoid_ops` and a working alternative sequence exists, the executor swaps that sequence in. Once the "label must exist" constraint is stored on `create_issue`, it also inserts an `ensure_label_exists` step before any `create_issue` that uses a label not already ensured. That guard is what makes memory change behavior instead of just sitting in a prompt. (The original take-home version described this guard, but the constraint half was never implemented. The offline harness showed no change across runs when the LLM ignored the prompt, so the guard was added afterwards.)

## How does capability synthesis work?

Scoped narrowly, on purpose: one real gap, not a general code-generation engine. The decomposer's tool catalog only lists what's actually in `capabilities`. When an instruction needs something not in that catalog, the decomposer is instructed to emit a step with `op_name = "NEEDS_SYNTHESIS"`, a plain-English `capability_request`, and a stable `requested_op_name`, an explicit flag rather than string-matching luck.

`synthesis.py` sends that request to the LLM asking for exactly one function: `def run(repo, params: dict) -> dict`, restricted to `datetime`/`collections`/`re`, with any write call gated behind `if not params.get("dry_run")`. Before it's trusted, the code goes through `agent/sandbox.py`. First comes an AST allowlist: only listed node types, no dunder or private names, attributes or strings, no frame/generator introspection attributes, no `str.format`, and imports limited to the allowlist with every alias checked. Then a dry-run against the target repo (reads allowed, writes suppressed) must return the right shape. Execution happens in a child process with a timeout and rlimits, using a minimal builtins dict and a restricted `__import__`. Two attempts are made, with the failure fed back to the model on the retry, and after that it gives up rather than pretending. Only after both checks pass is the capability written into `capabilities`, with the literal source stored as text. From then on it's a first-class catalog entry, and future runs skip generation and execute the stored source through the same sandbox.

The one concrete example built for this is `triage_summary_by_label_and_staleness`: group open issues by label and inactivity window, post the result as a new issue. Nothing in PyGithub does that in one call, so it's a believable gap. This is explicitly a narrow, same-owner-token trust model. In-process Python sandboxing is not a security boundary, and the generated code holds an authenticated `repo`. The honest scoping is "best-effort for one authenticated user's own scratch repo". Anything broader needs container or VM isolation (see the README threat model). The first version of this sandbox could be escaped through `getattr` chains, could not import its own allowed modules, and accepted `import re, os`. All three are fixed and covered by regression tests.

## What's the learning signal, and what changes between run 1 and run N?

Two logged, real metrics: API calls per run and latency per run, both grouped by `task_type`, both pulled straight from the `runs`/`steps` tables (`python main.py stats <task_type>` prints them chronologically, no massaging).

Concretely, for `create_labeled_issue`, the design assumes GitHub's `create_issue` rejects a label that doesn't exist yet with a 422. That assumption has **not** been re-verified against live GitHub, which may auto-create the label instead. In run 1 the agent hits the 422, recovers by creating the label and retrying, and records "label must exist before use in create_issue call" in `capabilities.known_constraints`. On later runs, the memory guard inserts `ensure_label_exists` before `create_issue`, so a brand-new label no longer costs a failed request.

Measured offline (`scripts/offline_learning_demo.py`, fake GitHub, scripted LLM that ignores memory hints; output in `results/offline_learning_demo.md`):
- New label: 5 GitHub calls on run 1, 4 calls on every later run. Without memory every run costs 5. The original code made 6 calls per run with no improvement and reported only 3 of them (`results/baseline_before_fix.json`).
- Existing label: 3 calls with the guard vs 2 without, because the guard pays one `GET /labels/{name}`.
- Once guidance exists, the decomposer makes a second LLM planning call per run (1 → 2).

The earlier "4 calls down to 1 or 2" figure was not measured and is withdrawn.

The synthesis path shows the same mechanism from a different angle. Run 1 of the triage-summary task pays for one code-generation LLM call plus a dry run. Run 2 finds the capability already registered and skips both. Offline: 1 → 0 code-generation calls and 4 → 3 GitHub calls. The earlier "9–12 s → ~1 s" latency figure was never measured and is withdrawn; latency needs a live LLM and GitHub.

## What I didn't build

Agent core is deliberately simple: linear decomposition, no replanning loop, a fixed built-in tool vocabulary. That was a scope call, not an oversight. The assignment rewards depth on fewer things over shallow coverage of all four, and memory plus the learning signal were where I wanted the depth to live. Given more time, the next thing I'd build is a second synthesized capability to prove the gap-detection path generalizes beyond one hand-picked example, and a confidence score on decompositions so the agent can flag "I'm not sure this is the right task_type" instead of silently misclassifying a genuinely novel instruction.
